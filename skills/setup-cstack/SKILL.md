# Setup cstack

Setup prepares one target repo. Run it from inside that repo. `<root>` is the plugin root, two directories up from this skill's base directory. It is safe to run again: every step converges on the same end state.

## Steps

0. **Choose the forge.** The forge is where issues, change requests and CI live: `github` (the default), `gitlab` or `local` (plain git, any remote or none). Take it from the `--forge` argument, else from an existing config's `forge`, else ask once with AskUserQuestion, defaulting to GitHub. A self-hosted GitLab also needs its host: `--forge-host <host>`, else ask. Below, `<forge flags>` is `--forge <forge>`, plus `--forge-host <host>` when set. Pass them to every `forge.mjs` call: until step 6 writes the config, they are the only place the choice lives.
1. **Find the repo.** Run `git rev-parse --show-toplevel` and `node <root>/gates/forge.mjs repo --json <forge flags>`, which gives the repo `path` and its `defaultBranch`. Stop if either fails. On GitLab the path may nest groups (`group/sub/project`).
2. **Read the existing config.** If `.cstack/config.json` exists, load it. Keep every value the user set. Fill only missing keys.
3. **Find the test command.** Look at the repo, not the user:
   - `package.json` scripts (`test`, then `test:unit`), the lockfile picks `npm`, `pnpm`, `yarn` or `bun`.
   - `pyproject.toml` or `pytest.ini` gives `["pytest", "-q"]`. `uv.lock` gives `["uv", "run", "pytest", "-q"]`.
   - `Cargo.toml` gives `["cargo", "test"]`. `go.mod` gives `["go", "test", "./..."]`.
   - A `Makefile` with a `test` target gives `["make", "test"]`.
   - Run the command once. Record whether it passes. A red baseline is a WARN for the user, not a reason to stop.
4. **Find the required checks.** Run `node <root>/gates/forge.mjs required-checks <base> --repo <repo> <forge flags>`. On GitHub it reads rulesets and branch protection. On GitLab it lists the jobs of the base branch's newest pipeline that may not fail. Use the names it prints. If it prints `none`, set `[]`. With no required checks the merge gate never merges by itself: under autonomy `send` it refuses until `required_checks` names the CI jobs, or until the user sets `allow_merge_without_checks: true` to merge with no CI. Set that key only when the user asks for it. Tell the user, and propose check names from the CI that ran on the base tip: `node <root>/gates/forge.mjs checks <sha> <forge flags>`, where `<sha>` is `git rev-parse origin/<base>` after `git fetch -q origin <base>`. On `local` there is no CI server: set `ci_command` (default: the test command from step 3), ask once whether to change it, and set `required_checks` to `["ci"]`. The merge gate runs `ci_command` in a clean worktree at each head and records the verdict under `.cstack/forge/`.
5. **Ask once.** Use AskUserQuestion for the decisions only the user can make, each with a default:
   - `paths_off_limits` (default: `.github/workflows/**`).
   - `paths_hidden` (default: `tests/acceptance/**`).
   - `docs_paths` (default: `null`). The merge gate merges a docs-only diff with no review round, and the verifier gate lets it pass with no test change. With `null`, any `.md`, `.txt` or `.rst` file anywhere counts as docs. With `[]`, no file counts as docs, so every change gets a review round. If markdown is product in this repo (skills, prompts, a content site), propose the globs that are only docs, such as `["docs/**", "README.md"]`.
   - `required_checks`, only when step 4 found none: the proposed names (default), or none.
   - `autonomy` (default: `send`, which means the merge gate merges once every check, the verifier and the review loop pass; choose `stop` to merge every PR yourself). When `required_checks` is still empty on `github` or `gitlab`, the default is `stop`. Say that `send` will not merge until required checks exist, unless the user also asks for `allow_merge_without_checks: true`.
   - Model per role (defaults: code `opus`, judge `fable`, review `sonnet`, gather `haiku`). Judge and review should differ from code.
6. **Write the config.** Start from `templates/config.json` in the plugin root (two directories up from this skill). Set `forge` to the choice from step 0, and `forge_host` when there is one. Write `.cstack/config.json` with 2-space JSON through Bash (for example `node -e` or `jq ... > .cstack/config.json`), never with the Write or Edit tool: on a re-run the guard blocks file tools on this path. Show the user the final file. Leave `permissions_allow` empty. It adds permission rules to the allowlists of the headless sessions cstack launches. As a list, such as `["Bash(make lint)"]`, it adds them to the worker, coordinator and e2e-author roles. As an object keyed by role, such as `{"e2e-author": ["Bash(agent-browser *)"]}`, it adds each list to that role only. The keys are `worker`, `coordinator`, `e2e-author` and `grader`; doctor fails any other key. Give a rule that reaches the network to the one role that needs it. The configured commands are already allowed, so a person adds rules here only when a session reports a refused call it needs.
7. **Ignore local state.** Make sure `.gitignore` has the two lines `.cstack/*` and `!.cstack/config.json`, so the run store and the repo profile stay local and only the config is committed.
8. **Create the labels.** Skip this on `local`, where labels are plain strings on the local records. For each state in `ready`, `in-progress`, `done`, `error`, `needs-human`, `investigate`, `proposed`, run `node <root>/gates/forge.mjs labels ensure "<prefix>:<state>" --repo <repo> <forge flags> --color <color> --description "<text>"`. It creates the label or updates it. Colors: ready `0e8a16`, in-progress `fbca04`, done `5319e7`, error `b60205`, needs-human `d93f0b`, investigate `1d76db`, proposed `c5def5`.
9. **Verify.** Run `cstack:doctor` on the repo. Before step 10 the only FAIL it may report is `config committed`, and `gitignore committed` may WARN: unit worktrees are cut from the base branch, so they get the config only once it is merged there. Fix any other FAIL first. Report the WARN lines. In Codex, a `FAIL hooks (codex)` line means Codex has not trusted cstack's hooks yet, so the guard does not run. Codex asks for that trust once, in `/hooks`, and only the user can give it. Ask them to open `/hooks`, trust the cstack hooks, and run doctor again. Never work around it with `--dangerously-bypass-hook-trust`.
10. **Commit on a branch.** Skip this step when doctor printed `PASS config committed` and no `gitignore committed` line other than PASS. `<ref>` is `origin/<base>` (run `git fetch -q origin <base>` first), or `<base>` on `local` with no `origin` remote. Never commit to or push the base branch: the guard blocks it, and the human merges.
    1. If the branch `cstack/setup` already exists, locally or on origin, an earlier setup change is still waiting. Tell the user to merge or delete it, and stop.
    2. Run `git switch -c cstack/setup <ref>`. Git carries the uncommitted config and `.gitignore` over. If the switch refuses because the current branch's `.gitignore` differs from `<ref>`'s, stash the two files and carry them by hand: `git stash push -u -- .cstack/config.json .gitignore`, `git switch -c cstack/setup <ref>`, `git stash pop`. If the pop conflicts on `.gitignore`, keep `<ref>`'s lines plus `.cstack/*` and `!.cstack/config.json`, run `git add .gitignore`, then `git stash drop`. If the switch refuses for any other reason, report its error and stop.
    3. Run `git add .cstack/config.json .gitignore` and `git commit -m "Set up cstack"`. Add no other file.
    4. With an `origin` remote, run `git push -u origin cstack/setup`.
    5. On `github` or `gitlab`, write a short body (what the config sets, and that worktrees need it on the base) to a temporary file outside the repo. Run `node <root>/gates/forge.mjs change create --head cstack/setup --base <base> --title "Set up cstack" --body-file <file> --json <forge flags>`. On `local` there is no change request: the branch is the proposal.
    6. Run `git switch -` to go back to the branch the user was on. The switch-back is deliberate: a config left here untracked would make the later pull refuse with "untracked working tree files would be overwritten". The config and the `.gitignore` change leave this checkout until the merge.
    7. Tell the user, in these words or close to them: cstack is dormant in this checkout until the change merges. Doctor reports `FAIL config`, the guard does not act here, and `.cstack/runs/` is not ignored. Launch no cstack work before the merge. Review and merge the change (on `local`, `git merge cstack/setup` into `<base>`, then push it if there is a remote). Then `git pull` on `<base>` (or `git fetch` and switch to `<base>`) brings the config back. Run `cstack:doctor`: setup is done when it exits 0.

## Rules

- Never overwrite a value the user set. Show a diff if a value would change and ask.
- Never commit to, push or merge the base branch. The only branch setup creates and pushes is `cstack/setup`.
- The only writes to the forge are the labels and the one setup change request.
