# Maintain a verification skill

A feature map rots the moment the app changes. This skill is the upkeep loop for a skill generated by `cstack:create-verification-skill`, or any project-local verification skill with a feature map. The unit of rigour is the feature, not every sentence. Cover every feature file from source and use every feature live. Do not turn every bullet into a terminal run.

Read the [cstack mode skill](../cstack/SKILL.md) first. Its subagent rules apply to the source wave.

## Outcomes

Pick one, and say which:

- **clean.** Every feature got source and live coverage. Nothing is worth shipping. No branch, no PR.
- **changed.** One PR ships proven doc, harness, or map corrections.
- **blocked.** Coverage could not finish, or a proven fix could not ship safely. Say exactly what blocked it.

## Edit scope

Edit only the verification skill's own directory: its `SKILL.md`, `features/`, and the harness scripts it owns. Never edit product code during a run. A behaviour the map describes that the app no longer has is either doc drift (fix the map) or a product regression (report it, do not paper over it in docs).

## Pass

0. **Locate the target.** Find the verification skill to maintain: the project-local skill whose body has launch and drive sections and a feature map, usually `.claude/skills/verify-*/`. Several candidates: ask which one. None: stop and point at `cstack:create-verification-skill` instead of inventing a target.

1. **Index hygiene.** Read the feature map README and glob its sibling files. Fix missing, extra, duplicate, or dead entries. Keep it light. Generate no inventory.

2. **Source wave.** Launch one read-only subagent per feature file, all at once. Use `Explore` (or the plugin's `cstack-explorer` agent) with config `models.gather`, and say "do not edit files" in the brief. Each one explains "how does this user-facing feature work?" from source, flags likely doc drift with citations, and returns one concise live-verification recipe. They never drive the app and never edit files. Return shape: feature summary, source entry points, likely drift or none, one recipe.

3. **Reconcile.** Every feature file has a returned summary. Merge overlapping recipes into as few app states as practical. Spot-check cited drift. Do not re-prove clean claims. Sweep recent churn for user-facing surfaces missing from the map. Call one missing only with a concrete source path.

4. **Live pass.** Required even when the source looks clean. You, the coordinator, do all the driving. Follow the verification skill's own launch model: one long-lived instance driven serially for servers and UIs, or a fresh isolated session per drive for short-lived CLIs. The skill's Launch section decides, not this one. Use every feature at least once. Hold three invariants for the whole pass, whatever fails:
   1. Never drive an instance you have not health-checked since it last did something surprising. Run doctor before the first drive, on each fresh session where sessions are the unit, and again after any failed drive. Where doctor cannot see the failure (a wedged UI on a healthy process), reset to a known state or relaunch. Do not hope.
   2. The evidence captured so far survives every cleanup. Check it at its named location. Do not assume.
   3. Nothing a drive started outlives its use. Clean failed-iteration residue whether the session is stuck, exited or shared. For a shared instance, clean the residue, not the instance.

   A doctor failure caused by skill drift is drift. Fix it under the edit scope and retry once. Restart only what the fix invalidated. Then call the pass `blocked`.

   A feature you cannot reach is `verified-unreachable` only with the concrete prerequisite (auth, entitlement, OS, external state) and the route you tried. If the map omits that prerequisite, that is drift.

   Drive every harness fix from triage live again before it ships. Tear down after the last drive of the run, including those re-proofs, so nothing outlives the run. The evidence stays, per the skill.

5. **Triage.**
   - A wrong or missing user-POV description is doc drift. Fix it.
   - Working behaviour the harness cannot drive is a harness gap. Fix it. A harness fix follows the same helpers rule as generation: scripts are executable and the skill body shows how to call them.
   - App behaviour that is actually broken is a product gap. Record it for the user. Keep it out of this PR.

6. **Ship or stop.** For `changed`: one PR of proven corrections. Re-read every changed file first. Write its title and body in the style of `cstack:file-pr`. Start the body with `Closes #N` only when an issue asked for this pass. For `clean` or `blocked`: no PR. Report the outcome and the coverage honestly.

Keep short run notes (features covered, unreachable prerequisites, confirmed drift, outcome) in a scratch location. Do not commit them.

## Report

- The outcome: clean, changed or blocked.
- Features covered from source and live, and any `verified-unreachable` with its prerequisite.
- Drift fixed, harness gaps fixed, product gaps found.
- The PR link for `changed`.
